# `main.cpp` 模块拆分设计

## 目标

在修复剩余协议问题之前，先对当前约 1156 行的 `src/main.cpp` 做一次行为保持的结构拆分。拆分后，`main.cpp` 只负责初始化和主循环编排，目标规模为约 150–250 行；设备控制、BLE、波形、Web 和日志分别放入职责明确的模块。

本阶段只改变文件结构和内部调用方式，不修改任何对外行为，也不借重构修复已知问题。

## 约束

- 遵守仓库 `AGENTS.md`：官方协议以 `docs/coyote` 为准，官方 Demo 以 `docs/Web Bluetooth` 为准，并避免不适合 ESP32 的过度防御性设计。
- Web 路径、请求参数、页面内容、HTTP 状态码和重定向行为保持不变。
- BLE 设备前缀、UUID、扫描和自动连接顺序、连接重试、MTU、回调职责及断连流程保持不变。
- V2/V3 波形数据、强度行为、BF 数据、发送周期、超时和现有日志文本保持不变。
- 不增加任务、互斥锁、队列、动态容器、继承、虚函数、事件总线或依赖注入框架。
- 本阶段不新增测试，也不修改现有测试预期。

## 方案选择

采用“文件职责拆分 + 轻量共享状态”。这是最适合纯重构的方案：大部分变化是现有数据和函数的原样搬迁，同时形成可管理的文件边界。

不采用以下方案：

- 独立管理器完全封装各自状态：边界更严格，但需要同步重设状态所有权、回调和恢复流程，超出纯拆分范围。
- 用大量 `extern` 将现有全局变量分散到不同文件：改动较小，但依赖仍然隐蔽，无法真正改善维护性。

## 模块结构

### `AppState.h`

保存跨模块共享、需要被页面或多个控制流程观察的运行状态，包括：

- 当前设备类型、连接状态、设备名称和地址；
- 自动连接、扫描和断连清理相关标志；
- 当前 A/B 强度以及确认、等待和输入许可状态；
- 是否发送、目标发送状态、波形索引和已选波形；
- 重连所需的设备身份和类型。

现有字段的类型、初值和语义保持不变。`AppState` 不拥有 BLE 客户端、BLE 特征或 HTTP 服务器。

### `AppLog.h/.cpp`

拥有当前 10 条日志的环形缓冲区和写入索引。公开追加日志以及按现有倒序向页面读取日志的简单接口。追加日志时继续添加相同的秒级时间戳，并原样写入串口。

### `Waveforms.h/.cpp`

保存全部 V2/V3 波形数组和长度，并根据设备类型、波形选择和索引返回当前波形。模块无可变全局状态，不负责计时、发送或强度控制。

### `BleManager.h/.cpp`

负责并拥有：

- BLE 客户端和 V2/V3 特征指针；
- 扫描回调、客户端回调和通知回调；
- 扫描结果、扫描与自动连接流程；
- FreeRTOS BLE 事件队列和现有丢弃计数；
- 连接、GATT 服务与特征发现、初始 V2 强度读取；
- V3 通知注册及重连后的 BF 写入；
- 手动断连、断连事件处理和客户端清理；
- V2 特征写入和 V3 B0 帧底层写入。

设备发现继续使用官方 Demo 的名称前缀逻辑：V2 为 `D-LAB`，V3 为 `47`。连接后继续通过对应服务和特征判断连接是否可用，不硬编码完整广播名称。

`BleManager` 通过 `pollEvent()` 暴露队列事件，不直接依赖 `OutputController`。

### `OutputController.h/.cpp`

拥有现有 `StrengthController`、`ResumePolicy` 和发送时钟，负责：

- V2/V3 A/B 强度调整；
- 当前 V3 强度命令准备、提交和回滚；
- B1 强度回应处理；
- V2/V3 波形发送及 100 ms 调度；
- 开始、停止和切换波形；
- 连接成功或断开后的现有输出状态更新。

它从 `Waveforms` 获取静态波形数据，通过 `BleManager` 的底层写入接口发送数据，并将页面需要显示的状态同步到 `AppState`。

### `WebUi.h/.cpp`

拥有端口 80 的 `WebServer`，负责：

- 生成当前 HTML 页面；
- 注册并处理 `/`、`/scan`、`/auto-connect`、`/connect`、`/disconnect`、`/start`、`/stop`、`/wave` 和 `/strength`；
- 保持现有参数解析、日志、返回状态和 302 跳转；
- 将连接和扫描操作交给 `BleManager`，将强度和波形操作交给 `OutputController`。

### `main.cpp`

以静态生命周期创建 `AppState`、`AppLog`、`BleManager`、`OutputController` 和 `WebUi`。它只保留：

- 串口、Wi-Fi AP 和 BLE 初始化；
- 模块初始化；
- BLE 事件的小型 `switch` 分派；
- 与当前实现相同顺序的主循环调用。

现有 `lib/DgLabControl` 保持独立，不在本阶段重新设计。

## 数据流

### BLE 回调

BLE 回调继续只执行适合回调上下文的现有操作：设置原子连接状态并尝试写入 `BleEvent` 队列。`main.cpp` 从 `BleManager::pollEvent()` 取出事件：B1 事件交给 `OutputController`，断连事件交给 `BleManager` 更新并清理连接状态。

### Web 请求

`WebUi` 使用现有条件解析参数。扫描、连接和断连请求调用 `BleManager`；强度、开始、停止和波形选择调用 `OutputController`。处理结束后保持现有页面跳转行为。

### 输出

`OutputController` 从 `Waveforms` 获取当前波形，按原有逻辑构造 V2 数据或 V3 B0 帧，再通过 `BleManager` 写入对应特征。模块拆分不合并当前强度和波形发送路径，也不修改它们的调用时机；这些属于后续协议修复阶段。

## 初始化与循环顺序

`setup()` 保持以下顺序：

1. 初始化串口并输出启动信息；
2. 建立隐藏 Wi-Fi AP 并输出地址；
3. 初始化 BLE；
4. 创建现有 16 项 BLE 事件队列；
5. 注册并启动 Web 服务；
6. 写入现有初始化日志和扫描时间。

`loop()` 保持以下顺序：

1. 处理 HTTP 客户端；
2. 消费 BLE 事件；
3. 清理断开的客户端；
4. 处理待发送强度；
5. 处理波形发送；
6. 处理自动扫描；
7. `delay(10)`。

## 状态与生命周期

- 所有应用模块对象均为静态生命周期，不在循环中分配。
- `BleManager` 独占 BLE 硬件句柄；`WebUi` 独占 HTTP 服务器；`AppLog` 独占日志缓冲区。
- 模块通过构造时保存的引用访问 `AppState` 和直接依赖，不设置全局服务定位器。
- 回调对象由 `BleManager` 持有，并通过固定所属实例指针访问队列和原子状态。
- 除现有 Arduino、BLE、`String` 和 `vector` 行为外，不增加新的动态内存使用模式。

## 错误处理

本阶段完整保留当前错误处理：

- BLE 服务或特征缺失时，继续断连并进入现有清理流程；
- 写入失败、无效参数、重复扫描和连接失败继续返回相同结果并记录相同日志；
- 队列满时继续只增加现有丢弃计数；
- 不调整连接重试次数、重试间隔、超时、MTU、队列容量或参数限制。

断连事件丢失兜底、相对强度载荷、B1 确认状态以及 B0 调度等已知问题不在本阶段顺带修复。

## 实施顺序

按可独立编译的步骤拆分：

1. 提取 `AppState`、`AppLog` 和 `Waveforms`；
2. 提取 `BleManager`；
3. 提取 `OutputController`；
4. 提取 `WebUi`，最后缩减 `main.cpp`；
5. 做完整回归验证并推送现有 PR。

每一步只提交能够通过现有自动验证的状态，避免留下中间不可编译提交。

## 验证与验收

不新增测试。每个可编译拆分步骤运行：

```text
pio test -e native
pio run -e esp32dev
```

同时人工核对：

- Web 路由、请求参数、页面文本、HTTP 状态码和重定向不变；
- V2/V3 UUID、设备前缀、波形数组和 BF 数据逐字节不变；
- `setup()` 和 `loop()` 的有效执行顺序不变；
- BLE 回调职责、发送间隔、连接重试及状态初值不变；
- 日志文本不变；
- 构建输出中的 RAM 和 Flash 使用量没有因拆分出现明显增长。

全部本地验证通过后推送现有 PR，并确认 GitHub Actions 中 Native tests 与 ESP32 firmware build 均通过。

本阶段没有硬件测试，因此最终结论只表述为“结构拆分通过现有自动验证”，不声称 BLE 实机行为已经验证。
