# ESP32 DG-LAB 控制器轻量 WebUi 设计

**日期：** 2026-08-31
**状态：** 已确认，待实施

## 背景

当前 `WebUi` 在每次访问根页面时，通过大量 `String +=` 动态拼接完整 HTML。页面使用 5 秒 `meta refresh` 整页刷新，控制操作通过状态变更 GET 请求和 302 跳转返回首页。

这种实现能够工作，但存在以下问题：

- 每次整页渲染都会产生多次不同大小的堆分配，长期运行可能增加 ESP32 堆碎片。
- 页面每 5 秒重新下载全部 HTML，产生不必要的 Wi-Fi 流量和同步 WebServer 工作。
- HTTP 页面生成与发送发生在 Arduino 主循环中，可能增加 100 ms BLE 输出周期的抖动。
- 页面状态、控制路由和 HTML 结构耦合在同一个 `WebUi.cpp` 中，后续修改不易验证。
- 302 跳转导致手机端操作反馈慢，并且页面会闪烁和丢失当前阅读位置。

## 目标

- 使用静态单页和小型 JSON API，同时改善 ESP32 性能与手机端体验。
- 页面首次加载后不再整页刷新。
- 保留现有同步 `WebServer`、`AppState`、`AppLog`、`BleManager` 和 `OutputController`。
- 保留扫描、连接、自动连接、断开、强度、波形、开始/停止、日志及断线恢复行为。
- 让 WebUi 保持 HTTP 适配层职责，不参与 BLE 协议编码或强度状态机。
- 不增加不适合 ESP32 的通用框架或过度防御逻辑。

## 非目标

- 不更换 ESP32 BLE 栈或同步 `WebServer`。
- 不引入 ArduinoJson、前端框架、异步 WebServer、WebSocket 或 SSE。
- 不修改 V2/V3 协议、100 ms 输出调度、B0/B1 状态机或断线恢复策略。
- 不在本次工作中增加 HTTP 身份认证、完整 CSRF 防护或 Wi-Fi 配置功能。
- 不增加文件系统、构建期前端打包器或 gzip 资源生成流程。
- 不重做视觉品牌；只做适合手机触控的小幅界面改版。

## 选定方案

采用“存放于 Flash 的自包含静态单页 + 显式 JSON API”。

浏览器负责标签页切换、DOM 局部更新、轮询节流和操作反馈。ESP32 只负责直接发送静态页面、输出有界 JSON，并将经过校验的动作请求转发给现有控制模块。

未采用的方案：

- 服务端 HTML 片段仍会频繁拼接字符串，并继续耦合页面与固件。
- WebSocket/SSE 实时性更高，但会引入连接生命周期、额外 RAM 和并发复杂度；本项目 1 秒刷新不需要这些能力。

## 架构与职责

### 浏览器单页

- 首次加载一个内嵌 CSS 和 JavaScript 的 HTML 页面。
- 提供“状态”“控制”“日志”三个底部标签页。
- 每秒读取一次状态；动作成功或失败后立即再读取一次状态。
- 只在需要时读取设备列表和日志。
- 只通过 DOM `textContent`、属性和 class 更新页面，不使用动态字符串构造 `innerHTML`。

### WebUi HTTP 适配层

- 注册静态页面、读取 API 和动作 API。
- 校验 HTTP 方法与请求参数。
- 调用 `BleManager` 和 `OutputController` 的现有公开接口。
- 将 `AppState`、扫描结果和固定日志环转成有界 JSON。
- 返回稳定的 HTTP 状态码和简短机器错误码。

### 现有模块

- `AppState` 继续拥有连接、强度、波形和发送状态。
- `AppLog` 继续保留最新 10 条日志。
- `BleManager` 继续拥有扫描、连接、GATT、通知与写入。
- `OutputController` 继续拥有强度请求、波形选择、发送意图和 B0/B1 状态。
- `main.cpp` 的模块编排不因 Web API 改变。

## 静态资源

新增：

- `src/WebAssets.h`
- `src/WebAssets.cpp`

`WebAssets.cpp` 定义一个 `PROGMEM` 自包含页面。HTML、CSS 和 JavaScript 位于同一个原始字符串中，避免额外静态资源请求和文件系统依赖。

根路由使用 Flash 资源发送接口直接返回该页面，不先复制成完整的动态 `String`。页面响应使用 `text/html; charset=utf-8` 和 `Cache-Control: no-cache`。API 响应使用 `application/json; charset=utf-8` 和 `Cache-Control: no-store`。这样页面可以重新验证资源，不会在固件升级后长期保留旧版本。

本阶段不进行 gzip 压缩。只有实测静态资源体积或传输时间成为问题时，才另行设计生成流程。

## HTTP API

### 读取接口

| 方法 | 路径 | 行为 |
|---|---|---|
| `GET` | `/` | 直接返回 Flash 中的静态单页 |
| `GET` | `/api/status` | 返回连接、强度、波形、发送和自动连接状态 |
| `GET` | `/api/devices` | 返回当前扫描结果；仅设备视图按需调用 |
| `GET` | `/api/logs` | 返回最新 10 条日志；仅日志页可见时调用 |

`/api/status` 返回固定字段：

```json
{
  "connected": true,
  "ready": true,
  "type": 3,
  "name": "47L121000",
  "strengthA": 42,
  "strengthB": 36,
  "confirmed": true,
  "waiting": false,
  "wave": "b",
  "sending": true,
  "autoConnect": true,
  "scanRevision": 123456
}
```

规则：

- `type` 使用 `0`、`2`、`3` 表示无设备、V2、V3，避免暴露内部枚举数值 `0/1/2`。
- 未连接时名称为空、强度为 0、`ready/sending/waiting/confirmed` 为 `false`。
- `confirmed=false` 表示页面显示的是预测值或尚未收到设备确认。
- `waiting=true` 表示 V3 正在等待匹配的 B1。
- `scanRevision` 使用现有 `lastScanFinished` 的无符号值。浏览器只比较它是否变化，不解释其时间含义；值变化且设备仍未连接时，浏览器重新读取设备列表。

设备列表返回：

```json
{
  "devices": [
    {"name":"47L121000","address":"aa:bb:cc:dd:ee:ff","type":3,"rssi":-51}
  ]
}
```

日志返回：

```json
{"logs":["12s: 已注册通知回调","11s: 连接成功"]}
```

设备名称和日志在固件端进行最小完整 JSON 字符串转义，包括引号、反斜杠和控制字符。浏览器端使用 `textContent` 呈现这些值。

### 动作接口

所有状态变更接口使用 `POST` 和 `application/x-www-form-urlencoded`，以便继续使用 `WebServer::arg()`，不增加 JSON 请求解析器。

| 路径 | 参数 | 调用行为 |
|---|---|---|
| `/api/scan` | 无 | 启动现有同步扫描；如自动连接成功则完成连接状态初始化 |
| `/api/connect` | `address`, `type` | 在当前扫描结果中解析身份并进行手动连接 |
| `/api/disconnect` | 无 | 手动断开并取消发送意图 |
| `/api/auto-connect` | `enabled=0|1` | 修改自动连接开关 |
| `/api/output` | `sending=0|1` | 调用开始或停止发送 |
| `/api/wave` | `type=a|b|c` | 选择内置波形 |
| `/api/strength` | `channel`, `value`, `method` | 调用现有强度请求接口 |

普通成功响应：

```json
{"ok":true}
```

强度成功响应保留现有请求状态语义：

```json
{"ok":true,"disposition":"queued"}
```

`disposition` 取值为 `prepared` 或 `queued`。被拒绝的请求返回失败，不把 `Rejected` 伪装成成功。

失败响应：

```json
{"ok":false,"error":"invalid_argument"}
```

使用以下 HTTP 状态：

- `400`：缺少参数、参数格式错误或参数越界。
- `404`：地址和类型未出现在当前扫描结果中。
- `409`：当前连接/清理状态不允许该动作。
- `503`：BLE 连接或传输动作失败。

错误码保持简短稳定，页面负责把错误码映射成中文提示。ESP32 不为前端生成长错误说明。

## 页面信息结构

### 顶部状态

顶部固定显示：

- ESP32 页面连接状态。
- BLE 已连接/未连接状态。
- 设备名称和 V2/V3 类型。

### 状态页

已连接时显示：

- A/B 当前强度。
- “已确认”“待设备确认”或“命令处理中”。
- 当前波形。
- 输出运行/停止状态。

未连接时显示：

- 扫描按钮和扫描进度。
- 自动连接开关。
- 当前扫描到的主机列表和 RSSI。

### 控制页

每个通道提供以下离散按钮：

- `-10`、`-5`、`-1`
- `+1`、`+5`、`+10`
- 归零
- 50%

不使用滑杆。离散变化量更容易预测，降低触控误跳到高强度的风险，并与 V3 相对命令及 V2 每级乘 7 的现有行为一致。

前端根据通道生成现有协议方法值：A 通道增加/减少/绝对为 `4/8/12`，B 通道为 `1/2/3`。50% 对 V3 发送绝对值 100，对 V2 发送现有页面级值 146，由固件沿用乘 7 的转换。

同页提供：

- 波形 A/B/C 选择。
- 一个明显的开始/停止输出按钮。
- 当前动作结果提示。

### 日志页

- 只显示 `AppLog` 中最新 10 条。
- 进入日志页时立即读取一次。
- 日志页可见时每 2 秒更新，离开后停止日志请求。
- 不增加分页、搜索、下载或持久存储。

## 浏览器状态与刷新

浏览器使用一个普通 JavaScript 对象保存最后一次状态，不使用状态管理库。

刷新规则：

- 页面加载后立即请求 `/api/status`。
- 页面可见时每 1 秒请求一次状态。
- 上一次状态请求未完成时跳过本次轮询，不排队重复请求。
- 动作开始时暂停定时状态请求；动作结束后立即读取一次状态并恢复定时器。
- 页面进入后台时停止状态和日志轮询。
- 页面恢复可见时立即同步状态，并根据当前标签页恢复相应定时器。
- 设备列表只在未连接且状态页需要展示列表时请求；手动扫描动作完成或 `scanRevision` 变化后立即刷新列表。

## 交互与错误处理

- 普通动作只禁用触发该动作的按钮，不锁死整个页面。
- 扫描是现有同步 3 秒调用；扫描按钮在请求结束前显示进行中并保持禁用。
- 强度 `prepared` 显示“待发送”，`queued` 显示“已排队”。
- `confirmed=false` 时在强度旁显示“待设备确认”。
- `waiting=true` 时显示“命令处理中”，但不禁止现有控制器支持的排队请求。
- 动作失败时显示短时页面提示，保留最后一次有效状态，然后立即尝试重新读取状态。
- 状态轮询失败时顶部显示“与控制器通信中断”；下一周期自然重试，不向 ESP32 日志重复写入轮询错误。
- 一个请求失败不能清空设备状态、日志或当前标签页。
- 页面不对 BLE 失败自行重试动作；重连和自动扫描仍由固件现有策略负责。

## 性能约束

- 不在根路由构造完整页面 `String`。
- 读取 API 的响应大小由固定字段、扫描候选数和 10 条日志上限约束。
- 每个 JSON 响应最多使用一个预留容量的局部 `String`；不设计通用动态 JSON 树。
- 页面轮询不得重叠，后台页面不得继续轮询。
- 日志和设备列表不得并入每秒状态响应。
- 前端不使用外部 CDN、字体、图片或运行时依赖。
- 不为此页面增加额外 FreeRTOS 任务。

## 代码变更范围

计划修改：

- `src/WebUi.h`
- `src/WebUi.cpp`
- `src/main.cpp`，将到期的 `OutputController::handleWaveSend()` 放在 `WebUi::handleClient()` 之前，减少较慢 HTTP 响应对 100 ms 输出的起始延迟
- `README.md`，更新页面行为和 API 使用说明

计划新增：

- `src/WebAssets.h`
- `src/WebAssets.cpp`

计划移除：

- `WebUi::makeHtml()`。
- 5 秒 `meta refresh`。
- `/scan`、`/connect`、`/disconnect`、`/auto-connect`、`/start`、`/stop`、`/wave`、`/strength` 的旧状态变更 GET 路由。
- 依赖 302 跳转刷新状态的交互。

不修改协议模块、波形表和 BLE 回调实现。

主循环仍先处理 BLE 事件和断连清理，然后执行一次到期输出、处理一个 Web 客户端、处理自动扫描并短暂让出 CPU。Web 动作最迟在下一次约 10 ms 的循环中影响输出状态，不为此增加并发任务。

## 验证与验收

### 固件构建

- 运行 ESP32 PlatformIO 固件构建。
- 记录改造前后 RAM 和 Flash 使用量。
- 检查静态页面位于 Flash，根路由不构造整页动态字符串。
- Native 测试环境可用时运行现有协议与状态机测试；Web 改造不得改变结果。

### HTTP 接口

在 ESP32 上逐项验证：

- 所有读取 API 返回合法 JSON 和正确 Content-Type。
- 所有动作 API 的正常参数能够调用现有行为。
- 缺参、非法通道、非法方法、越界值、未知设备和错误连接状态返回约定状态码。
- 强度响应能区分 `prepared`、`queued` 和失败。
- 动作后页面立即同步，不依赖整页刷新。

### 浏览器

- 验证 320、375、390、430 px 手机宽度以及普通桌面宽度。
- 三个标签页可用，刷新后默认回到状态页即可，不持久化标签选择。
- 连续运行至少 10 分钟，不出现重叠轮询、页面卡死或持续下降的可用堆趋势。
- 页面转入后台后停止请求，恢复可见时立即同步。
- 设备名称和日志中的特殊字符不会破坏 JSON 或创建 HTML 元素。

### 真机 BLE

分别使用 DG-LAB V2 和 V3 验证：

- 扫描、手动连接、自动连接和断开。
- A/B 强度增减、归零和 50%。
- 波形 A/B/C 选择及开始/停止。
- V2 强度通知显示。
- V3 `prepared`、`queued`、B1 确认和超时显示。
- 意外断线后的既有同设备恢复策略。
- 持续波形输出时打开页面并连续操作，不出现由 HTTP 轮询引起的 BLE 断连、写入失败或明显输出停顿。

## 成功标准

- 用户在手机上操作时不再经历整页闪烁和 302 跳转。
- 页面状态通常在 1 秒内同步，控制动作完成后立即同步。
- ESP32 不再为每次页面刷新拼接完整 HTML。
- 设备列表和日志不会进入每秒轮询响应。
- 所有现有 DG-LAB 控制行为和恢复语义保持不变。
- 实现保持小型、无新增运行时依赖，并通过固件构建和 V2/V3 真机验收。
